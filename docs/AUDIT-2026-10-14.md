# FarmFlow — production readiness audit

**Date: 2026-10-14. Baseline: `main` at `7386242`** (`fix(release): a flaky network must not leave
you guessing whether production moved (#87)`).

⚠ **The working tree was not clean and it changed during the audit.** Seven files were uncommitted
when I started and the set grew while I worked — somebody was actively fixing a bug class I had
raised as a candidate finding. One finding was withdrawn as a result (see
[Resolved during the audit](#resolved-during-the-audit)). Every finding below was re-verified
against the tree as it stood at the end. Re-run the checks before acting; a repository under active
edit is not a stable baseline.

No application code, schema, migration, configuration or production data was modified. Nothing was
run against production.

---

## 1. Executive summary

**Assessment: not ready to take payment today, for one reason that is already fixed and unmerged.
Everything else is in better shape than a project at this stage usually is.**

The engineering substrate is genuinely strong, and it is worth saying so precisely because the
findings below are blunt. 2,918 unit and render tests pass in 28 seconds across 262 files.
`tsc --noEmit` is clean. ESLint reports one warning and zero errors. The dead-import check passes.
Tenant isolation is enforced at the database by RLS rather than only by query discipline. All 27
routes that issue a `DELETE` write an audit event, and I verified that by call rather than by
import. The test suite is unusually sophisticated about its own failure modes — guards derive their
file sets from `git ls-files` instead of hand-kept lists, strip comments before scanning so the
fix's own documentation cannot satisfy the scan, and assert `helper\s*\(` rather than a bare mention.
That discipline is the single best thing about this codebase and it is why this audit found fewer
live defects than the module count would predict.

**What stops a launch:**

- **One live, exploitable account-takeover path on the public signup endpoint.** It has a written
  fix, two new tests, and a verified exposure count — in PR #78, open and unmerged. Since merging is
  deploying here, the vulnerability is in production for as long as that PR sits.
- **Non-idempotent writes are automatically retried, and the eight tables that hold money have no
  unique constraint to stop a duplicate.** Attendance and rainfall are protected; labour, expenses,
  stock movements, picking, processing, sales and dispatch are not.
- **A per-user location restriction that the admin UI offers and 134 of 137 routes ignore.**

**What is sound:** authentication and session handling (the deleted-account hole is genuinely
closed), tenant scoping on reads, SQL injection posture, AI tenant scoping, audit coverage on
deletes, timezone discipline, migration tooling, and the test harness itself.

**The honest framing:** the gap between FarmFlow and production-ready is roughly one merge, one
schema decision about idempotency, and a decision about whether the location-scoping feature should
be enforced or withdrawn. That is a short list. It is not a rewrite.

### Request path

```
Browser (components/*, hooks/use-abortable, lib/single-flight)
  → app/api/**/route.ts
      requireSessionUser()            lib/server/auth → lib/auth-server
      requireModuleAccess(module)     lib/module-access  (plan → tenant_modules → user_modules)
      resolveScopedSessionUser()      owner preview-tenant translation
      resolveActiveEstate()           estate filter from query param + cookie
      normalizeTenantContext()        lib/tenant-db
  → runTenantQuery(sql, ctx, query)   lib/tenant-db
      client.transaction([
        set_config('TimeZone','UTC'),
        set_config('app.tenant_id', …),   ← what RLS policies read
        set_config('app.role', …),
        <the caller's query>
      ])
  → Neon Postgres, RLS enforced via the app_runtime role (APP_DATABASE_URL)
```

Two clients exist and the distinction is load-bearing: `sql` (runtime, least-privilege, RLS
enforced) and `adminSql` (schema owner, DDL and self-healing). `adminSql` **falls back to `sql`**
when no owner URL is set, which is why `isAdminDbConfigured` exists separately from
`isDbConfigured`.

### Critical data flows

**Labour cost — the spine.** `attendance_records` → `labour_assignments` → the `labour_cost`
**view** (`scripts/117`, redefined by `scripts/118`) → read by **20 routes** including
`cost-per-kg`, `season-pl`, `season-summary`, `finance-balance-sheet`, `accounts-totals`,
`intelligence-brief` and `exports/ops`. The view is pinned `security_invoker` by a migration that
`RAISE EXCEPTION`s if the option is lost — without it, `app_runtime` would read every tenant
through the view. That guard is the right shape and worth preserving.

**Harvest chain.** `picking_records` → `processing_records` → `dispatch_records` → `sales_records` /
`booked_revenue` (view, `scripts/121`). The picking day-budget work that was the open risk in
`docs/COMMERCIAL-LAUNCH.md` has since landed (#55, #75, #79, #85, plus `scripts/152`), so picking
and day-work now share one day budget.

**Money reads.** `booked_revenue` resolves four different kg column spellings into one, and
`cost-per-kg` divides by it. Revaluation is excluded from cost totals by four dedicated tests.

**External integrations.** Anthropic (with an undocumented fallback chain to OpenAI then Groq in
`lib/server/agents/ai-model.ts`), Alpha Vantage (coffee prices, cached 22h), WeatherAPI, TheNewsAPI,
Resend, Razorpay (built, inert), PostHog (EU, via `/ingest` rewrites), Sentry (three runtimes).

**Background work.** One Vercel cron at 02:00 UTC hits `/api/cron/orchestrator`, which fires ten
agents in a single `Promise.allSettled` under `maxDuration = 300`.

## 3. Findings

Severity rationale used throughout:

- **P0** — live, reachable, and causes loss (of money, of data integrity, or of an account) with no
  compensating control.
- **P1** — a confirmed defect or a missing security control with a plausible path to harm, but
  gated behind something: low probability, an empty table, or requiring an authenticated actor.
- **P2** — real, worth fixing, but degrades rather than breaks; or a cost/abuse exposure rather
  than a correctness one.
- **P3** — hygiene, documentation, and deferred architectural debt.

### P0-1 — Account takeover on the live public signup endpoint

**Files:** `lib/server/onboarding/signup.ts:211` (on `origin/main`), `app/api/auth/signup/route.ts`,
`lib/server/onboarding/provision-tenant.ts`

**Evidence.** `/api/auth/signup` is unauthenticated — a public page rate-limited on IP+email and
nothing else. `createOrRefreshSignupRequest` issues `password_hash = ${passwordHash}` as an
`UPDATE` against an existing unprovisioned signup request, then re-sends the verification link to
the address already on that row. Provisioning later reads `signupRequest.password_hash` to create
the estate's admin user. I confirmed the vulnerable `UPDATE` is still present on `origin/main` at
the audit baseline, and that PR #78 is `state: OPEN, mergedAt: null`.

**Realistic impact.** A stranger who knows the email address of someone mid-signup POSTs the public
form with their own password. The stored hash becomes the stranger's. The victim receives a
"verify your signup" email they are genuinely expecting, clicks it, and provisioning creates the
estate's **admin** account with the stranger's credentials. Nothing errors at any step. The
attacker owns a new tenant; the victim owns nothing and has no signal that anything went wrong.
PR #78 reports five production rows in the exploitable state at the time it was written.

**Severity rationale.** P0 on three counts: the entry point is public and unauthenticated, the
outcome is full control of a tenant, and the fix already exists so the only thing keeping it live is
an unmerged branch. On this project merging is deploying, so "open PR" and "unshipped fix" are the
same state.

**Validation.** PR #78's description contains the end-to-end trace, and its author states they
verified it in code rather than taking the scanner's report at face value. Two tests ship with it:
`tests/signup-credential-cannot-be-overwritten.test.ts` and
`tests/render/verify-email-tells-you-the-password-was-kept.test.tsx`.

**Recommended fix.** Merge PR #78. Do not re-derive the fix. Afterwards, check whether any of the
five exploitable rows was actually overwritten — compare `signup_requests.updated_at` against
`verification_sent_at` for unprovisioned rows, and treat a gap as a row to contact by hand.

### P1-1 — Automatic retries can duplicate a financial write, and no money table can refuse the duplicate

**Files:** `lib/tenant-db.ts:79-100` (`runTenantQuery`), `:105-130` (`runTenantQueries`),
`:134-160` (`runTenantTransaction`)

**Evidence.** All three helpers loop `for (let attempt = 1; attempt <= MAX_TRANSIENT_RETRIES; …)`
with `MAX_TRANSIENT_RETRIES = 3`, retrying whenever `isTransientConnectionError` matches. That
predicate (`:40-54`) keys on substrings including `fetch failed`, `signal is aborted`,
`aborted without reason`, `econnreset` and `etimedout`. **Those are exactly the errors that cannot
distinguish "the request never arrived" from "the request committed and the response was lost."**
The query is wrapped in `client.transaction([...])`, so a single attempt is atomic — but a retry
after a successful-but-unacknowledged commit re-executes the whole transaction.

Roughly 40 route files put `INSERT` / `UPDATE` / `DELETE` statements through these helpers, among
them `labor-neon`, `expenses-neon`, `transactions-neon`, `picking-records`, `processing-records`,
`sales`, `dispatch`, `rainfall`, `journal`, `receivables`, `worker-ledger` and `import-bulk`.

I then checked whether the database would reject a duplicate. It would not, for the ones that
matter:

| Table | Unique constraint | Protected? |
|---|---|---|
| `attendance_records` | `UNIQUE (tenant_id, worker_id, attendance_date)` — `scripts/67-attendance.sql:31` | **yes** |
| `rainfall_records` | `UNIQUE (tenant_id, record_date, estate)` — `scripts/146` | **yes** |
| `labor_transactions` | none found | no |
| `expense_transactions` | none found | no |
| `transaction_history` | none found | no |
| `picking_records` | none found | no |
| `labour_assignments` | none found | no |
| `processing_records` | none found | no |
| `sales_records` | none found | no |
| `dispatch_records` | none found | no |

There is no server-side idempotency mechanism for business writes. `lib/single-flight.ts` is an
in-process flag that solves the client double-tap and cannot see a server-side retry;
`lib/abortable.ts` is deliberately reads-only for a closely related reason, and its header comment
already articulates the exact hazard ("the client reports failure for a write that committed, the
user retries, and you get duplicate records").

**Realistic impact.** One flaky Neon round trip during a muster save or an expense entry produces
two identical rows. Both land in `labour_cost`, so labour cost, cost per kg, block attribution,
P&L and payroll all inflate by that row. Nothing throws and nothing is logged, because from the
application's point of view the retry succeeded. This is the project's signature failure mode: a
confident wrong number. The rate depends entirely on Neon's connection reliability, which I did not
measure.

**Severity rationale.** P1 rather than P0 because it needs a transient network failure at a precise
moment, and because the two highest-frequency write paths (attendance, rainfall) happen to be the
two that are protected. It is not P2 because the damage is silent, lands in money, and is very hard
to detect after the fact — a duplicated expense looks exactly like two genuine expenses.

**Validation method.** In a dev harness, wrap `client.transaction` so the first call commits and
then throws `new Error("fetch failed")`, call an expense `POST`, and count rows. Expect two. The
same harness against `attendance` should produce one plus a constraint error, confirming the
asymmetry.

**Recommended fix.** Options in rough order of preference: (a) split the helpers so only reads
retry and writes surface the ambiguity to the caller; (b) add an idempotency key supplied by the
client and a `UNIQUE (tenant_id, idempotency_key)` on each write table, which also fixes the
double-tap case properly; (c) add natural-key unique constraints where a natural key exists. Note
(c) alone changes a silent duplicate into a visible error, which is an improvement even if (a) or
(b) never ship. Whichever is chosen, tamper-test it: force the retry and prove the row count.

### P1-2 — Per-user location scoping is offered in the admin UI and enforced in 3 of 141 routes

**Files:** `lib/location-access.ts:50-60` (semantics), callers:
`app/api/attendance/workers/route.ts`, `app/api/locations/route.ts`,
`app/api/dashboard/bootstrap/route.ts`. Admin surface: `components/tenant-settings-page.tsx`,
`app/api/admin/user-locations/route.ts`.

**Evidence.** `getAccessibleLocationIds` is documented as returning `null` for unrestricted and a
possibly-empty **allow-list** once any `user_locations` row exists for the user — "a location absent
from it is NOT accessible". That is the correct, fail-closed semantic, and PR #32 fixed it to
behave that way. But a repository-wide search finds only three callers, two of which are themselves
about locations and workers. Every other data route — `expenses-neon`, `labor-neon`,
`transactions-neon`, `inventory-neon`, `sales`, `dispatch`, `processing-records`, `rainfall`,
`picking-records`, `season-pl`, `cost-per-kg` and the rest — filters by `tenant_id` and the active
estate, never by the user's permitted location set.

The admin path to create those rows is reachable: `app/api/admin/user-locations/route.ts` exists and
`components/tenant-settings-page.tsx` references it.

**Realistic impact.** A tenant admin restricts a writer to one block, reasonably believing that is a
restriction. The writer can still read and write every other block's expenses, labour, stock,
sales, processing and rainfall — all of it, through the normal UI. For an estate that brings in a
contractor or a per-block supervisor, that is a confidentiality and integrity failure in exactly
the place the product promised a boundary.

**Severity rationale.** P1, not P0, for one specific reason: STATUS.md records `user_locations` as
**0 rows across all tenants** as of 2026-09-21, so nobody has used the feature and there is
probably no live exposure. I could not re-verify that count (see §5). It is not P2 because this is
a security control that *appears* to work — the worst kind to get wrong — and the exposure becomes
live the first time any admin clicks the button.

**Validation method.** On a dev tenant, insert one `user_locations` row for a `user`-role account,
then call `/api/expenses-neon` and `/api/labor-neon` as that user and check whether rows from
non-permitted locations come back. Expect that they do.

**Recommended fix.** Decide first whether this feature is wanted. If yes, it needs enforcement at a
chokepoint rather than 130 call sites — most plausibly inside the estate-filter layer that every
route already calls, so a new route inherits it. If no, remove the admin UI and the table, because
an unenforced control is worse than an absent one. Either way, add a derived guard: enumerate
routes that read a location-scoped table and assert each one consults the allow-list, so route 142
is covered on the day it is written.

### P1-3 — STATUS.md documents an open security hole that is closed

**Files:** `STATUS.md` ("Known and deliberately not fixed", final two bullets) vs
`lib/auth-server.ts:155-200`

**Evidence.** STATUS.md says: *"⚠ The auth half is still open, and it is the more general defect.
`lib/auth-server.ts:157-183` falls through to trusting the JWT's own claims when its `users` lookup
returns nothing, so a deleted account keeps a valid session with its role until the token expires."*

The current code does the opposite. When the lookup returns no rows it throws `Unauthorized`, under
a 25-line comment explaining why it deliberately does not fall through to either the JWT claims or
the username lookup, and recording that the behaviour was verified 11/11 on prod and 10/10 on dev
across six tenants. This landed in `c80b4b9` (`fix(auth): a deleted account kept working for up to
30 days (#51)`). CLAUDE.md's auth section has been updated to match; STATUS.md has not.

**Realistic impact.** No runtime impact. The impact is on triage: STATUS.md is the file the project
instructions tell a reader to start with, and it currently carries a bolded, warning-marked claim
that the system has a month-long session-revocation hole. Anyone planning security work will either
re-fix something that is fixed or lose confidence in the rest of the file. CLAUDE.md documents two
previous instances of exactly this failure (the `gh` capability claim, the ruleset status), which
suggests the pattern rather than the instance is the thing to address.

**Severity rationale.** P1 because of what it is attached to. A stale "we have an auth hole" note in
the canonical status document misdirects the scarcest resource on this project, which is the
maintainer's attention.

**Recommended fix.** Correct the entry to record #51 as the fix, keep the surrounding note about not
inferring from deletion counters (that reasoning is still sound and still useful), and re-date the
file. STATUS.md's own header says it was last reviewed 2026-09-21, three weeks before this audit.

### P2-1 — Rate limiting covers 14 of 82 write routes

**Evidence.** Of 82 route files exporting `POST`, `PUT`, `PATCH` or `DELETE`, 14 call
`checkRateLimit`. The authentication surface is well covered — signup, resend-verification,
verify-email, confirm-email-change, forgot-password, reset-password all rate-limit on sensible
composite keys. The business write surface has none: `expenses-neon`, `labor-neon`,
`transactions-neon`, `inventory-neon`, `attendance`, `attendance/assignments`, `sales`, `dispatch`,
`processing-records`, `locations`, `journal`, `import-bulk`. Cron routes are gated by `CRON_SECRET`
(fails closed at 503 when unset) and admin routes by role, so those are defensible omissions.

**Realistic impact.** Low today: every one of these requires an authenticated session, and there
are four tenants. It matters at the moment signups open — a leaked or hostile session can write
without bound, and `import-bulk` in particular is an expensive endpoint. This is a cost and
availability exposure on Neon and Vercel more than a data one.

**Severity rationale.** P2 — authentication is the real control here and it is present. Raised
because the blast radius grows with the customer count, and `docs/COMMERCIAL-LAUNCH.md` plans for
10-30 new estates.

**Recommended fix.** A default limit applied at a shared wrapper rather than per route, with
per-route overrides for the expensive ones. A derived test asserting every write route resolves a
limit would stop the next route shipping without one.

### P2-2 — `/api/ai-validate` calls a language model with no rate limit and no module gate

**Files:** `app/api/ai-validate/route.ts:139` (`requireSessionUser()`), `:188`
(`client.messages.create`)

**Evidence.** Every other AI route pairs a model call with both a module gate and a rate limit:
`ai-assistant` uses `checkRateLimit("aiAssistant", sessionUser.tenantId)`, `ai-analysis` uses
`requireModuleAccess("ai-analysis")` plus `checkRateLimit("aiAnalysis", …)`, `ai-season-compare`
uses `requireModuleAccess` plus a limit. `ai-validate` calls `requireSessionUser()` and goes
straight to the model. Its data reads are correctly tenant-scoped through `runTenantQuery`, so this
is a spend exposure, not an isolation one.

**Realistic impact.** Any authenticated user in any tenant can invoke paid model calls in a loop.
Uncapped third-party spend with no circuit breaker.

**Severity rationale.** P2 — requires authentication, no data exposure, and the per-call cost is
small. The reason to fix it is that it is the one inconsistency in an otherwise uniform pattern,
which is how it will be missed again.

**Recommended fix.** Add `checkRateLimit("aiValidate", …)` and decide whether it needs a module
gate. Also worth noting: `ai-assistant` keys its limit on `tenantId`, so one user can exhaust the
whole estate's allowance — probably acceptable, worth being deliberate about.

### P2-3 — No environment-variable validation anywhere

**Evidence.** 56 distinct `process.env.*` identifiers are referenced across `app/` and `lib/`. There
is no env schema, no boot-time validation, and no startup assertion — I searched for a validating
module and found none.

**Realistic impact.** A missing or misspelled variable degrades silently and per-feature rather than
failing fast. This codebase has an expensive precedent documented in CLAUDE.md: a malformed
`connect-src` entry meant **client-side Sentry reported nothing for months** while server-side
Sentry kept working, so the project did not look broken. Several variables have fallback chains
that make a misconfiguration even quieter — `APP_DATA_ENCRYPTION_KEY` silently falls back to
`NEXTAUTH_SECRET` (coupling field decryption to session-secret rotation), and the agent model
resolver falls back from Anthropic to OpenAI to Groq.

**Severity rationale.** P2 — nothing is broken right now, but this is the mechanism by which a
future misconfiguration becomes invisible, in a codebase whose dominant failure mode is already
silence.

**Recommended fix.** One module that declares each variable as required-in-production or optional,
throws at boot for the former, and logs once for the latter. Vercel's build step is the right place
to fail.

### P2-4 — The digest fan-out is sized for 5-10 tenants

**Files:** `lib/server/agents/weekly-digest-agent.ts:691-693`,
`lib/server/agents/daily-digest-agent.ts:526`, `app/api/cron/orchestrator/route.ts:22,117`

**Evidence.** The weekly digest's own comment reads *"Process tenants in parallel batches of 3 —
avoids serial bottleneck with 5-10 tenants"*, with `BATCH_SIZE = 3` and one Claude call per tenant.
The daily digest has an independent `BATCH_SIZE = 3`. Both run inside one orchestrator invocation
with `maxDuration = 300` that also fires eight other agents in the same `Promise.allSettled`.
Mondays run both digests. `tenant-smoke-agent.ts:669` reads its targets from
`parseTenantSmokeTargetsEnv()` — a hand-maintained env var rather than a query against `tenants` —
and iterates them fully sequentially, so new estates get no synthetic monitoring at all.

**Realistic impact.** At 30 tenants the weekly digest alone plausibly needs 150-250s inside a 300s
budget shared with nine other agents. The failure mode is a truncated function: some estates get
their digest, some do not, and nothing reports which. Harmless at four tenants.

**Severity rationale.** P2 today, and it becomes P0 the week a marketing push lands. Carried from
`docs/COMMERCIAL-LAUNCH.md` Gate 8a.

**Recommended fix.** Measure real per-tenant duration from `agent_runs` first, then raise the batch
size or move each digest to its own cron path with its own budget. Derive smoke targets from
`tenants` and sample.

### P2-5 — `tableHasLocationColumn` is duplicated verbatim in four routes and runs per request

**Files:** `app/api/accounts-totals/route.ts:13-23`, `app/api/accounts-summary/route.ts:13-23`,
`app/api/labor-neon/route.ts`, `app/api/expenses-neon/route.ts`

**Evidence.** The same nine-line helper, querying `information_schema.columns` for a `location_id`
column, appears identically in four route files. It runs on each request (two such lookups per
request in the accounts routes), is not cached, and uses `accountsSql` directly rather than
`runTenantQuery` — correctly, since `information_schema` has no `tenant_id` and RLS does not apply.

**Realistic impact.** Two avoidable database round trips on every accounts request, and four copies
of a schema assumption that will drift. Not a correctness problem.

**Severity rationale.** P2 for the duplication (area A explicitly asks for it), P3 for the
performance. Grouped here.

**Recommended fix.** One shared helper in `lib/server/` with a module-level cache — the column
either exists or it does not, and it cannot change within a deployment.

### P2-6 — `cost-per-kg` can publish a partial cost total as complete

**File:** `app/api/dashboard/cost-per-kg/route.ts:20-31` (`tryQuery`), `:125-148`

**Evidence.** `tryQuery` deliberately swallows "relation does not exist" errors and returns
`{ rows: [], ok: false }`, rethrowing everything else — a sound design, and the rethrow means a
transient failure 500s rather than reporting zero. But the consumer then computes
`laborCost = Number(laborResult.rows[0]?.total_cost) || 0` regardless of `ok`, and reports
`hasData = laborResult.ok || expenseResult.ok` — an **or**. If the `labour_cost` view is missing
while `expense_transactions` is present, the route returns `hasData: true` with a `costPerKg` that
omits labour entirely.

**Realistic impact.** Labour is the dominant cost on these estates, so cost per kg would read far
too low while declaring itself valid. Probability is low: the view exists in both databases and is
guarded by a migration that raises if it loses `security_invoker`. But the degradation is silent and
the metric is the headline number of the costing story.

**Severity rationale.** P2 — low probability, high consequence, trivially fixable. It is the same
family as the work in flight, so the cheapest moment to fix it is now.

**Recommended fix.** Make the denominator honest: if any component read failed, report
`costPerKg: null` and name the missing component, exactly as
`lib/server/incomplete-read.ts`'s `failedReads()` already does for the other routes. Change the
`||` to an `&&` at minimum.

## Resolved during the audit

**Withdrawn: "a failed read is reported as a zero."** I raised this as a P1 candidate on strong
evidence — `.catch(() => [])` on tenant queries in `season-pl`, `ai-season-compare`,
`recent-activity`, `cost-per-kg` and `lots/[lotId]`, which turns a database failure into
`Number(undefined) || 0`. By the end of the audit all five were fixed in the working tree, behind a
new `lib/server/incomplete-read.ts` and a new guard, `tests/a-failed-read-is-not-a-zero.test.ts`.

I verified the fix rather than accepting it: I re-implemented the guard's scan in a scratch script
and ran it independently. Its pathspec resolves **141 of 141** route files (it misses none), and
scanning every `route.ts` under `app/` finds **zero** remaining instances. The guard also strips
comments before matching, which is load-bearing here because the fix documents the old pattern
verbatim in four files and a raw-source scan would match its own explanation.

Two notes worth keeping. First, `app/api/dashboard/cost-per-kg/route.ts:59` now carries a comment

## 4. Untested assumptions and what could not be verified

Listed because an audit that does not say what it missed is not usable.

**Blocked by this environment:**

  permission classifier. So these remain unverified and are taken from documentation:
  whether `scripts/74-tenant-commercial-access.sql` is applied (CLAUDE.md says no, verified
  2026-07-28); the `user_locations` row count that holds P1-2 at P1 rather than P0 (STATUS.md says
  0, 2026-09-21); current tenant activity; and the exploitable `signup_requests` count in P0-1
  (taken from PR #78).
- **`pnpm schema:rls` and `pnpm schema:isolation`** — the two checks that actually prove tenant
  isolation holds — need a database connection and were not run. **RLS is therefore asserted from
  code and migrations, not demonstrated.** This is the single most important gap in the audit:
  tenant isolation is the product's core security property and I verified its implementation, not
  its behaviour.
- **E2E suites** (23 specs). Require a running server and a seeded database. Not run.
- **Account tiers** for Vercel, Neon and Resend, each of which bears on a finding.

**Not attempted, and a real gap in coverage:**

- **Area F (UX) is largely not assessed.** I did not launch the application. I read component
  structure and sizes, but every claim about navigation, empty states, error states, responsive
  layout, modal behaviour and "actions that appear to succeed without persisting" would require
  driving the UI. Treat the UX column in §6 accordingly.
- **No test-coverage measurement.** 2,918 tests pass and 100 of 137 route directories are named

- **Dependency vulnerabilities.** No `pnpm audit` was run.
- **The newly-landed picking work** (#55, #75, #79, #85, `scripts/152`) — the either/or day budget,
  the paid-how field, and the edit path — is three weeks old, has never been used by a real estate
  (`picking_records` was 0 rows at last measurement), and faces its first harvest in weeks. It is
  the largest untested-in-production surface in the product and I could not exercise it.
- **The eight-month-dormant harvest chain.** Processing, dispatch, sales and pepper last saw real
  rows in February. I read the code; nothing has run it.

## 7. Phased remediation plan with regression tests

### Phase 0 — Ship what is already done (hours)

1. Merge PR #78. Then audit the five unprovisioned `signup_requests` rows for evidence of an actual
   overwrite, and contact any affected estate by hand.
2. Commit `lib/server/incomplete-read.ts`, its guard, and the six route changes. Confirm `pnpm test`
   and `pnpm typecheck` are green on a clean tree, not a dirty one.
3. Correct STATUS.md (P1-3) and re-date it.

**Regression tests:** both of PR #78's tests must be in the merge. Add one asserting that a signup
`POST` against an existing unprovisioned request leaves `password_hash` unchanged — a direct
behavioural assertion, not a scan.

### Phase 1 — Close the write-integrity hole (days)

4. Decide the idempotency approach for P1-1. My recommendation: split the retry so reads retry and
   writes do not, then add `UNIQUE (tenant_id, idempotency_key)` to the eight unprotected tables and
   have the client supply the key. That fixes the server retry and the double-tap with one
   mechanism.
5. Fix P2-6 while the costing routes are open.

**Regression tests:**
- A harness that commits then throws `fetch failed` inside `client.transaction`, asserting exactly
  one row lands for an expense, a labour entry, and a stock movement. **Tamper-test it**: revert the
  fix and confirm it reports two.
- A derived test that enumerates tables written by any route and asserts each has either a unique
  constraint or an idempotency column — so table nine is covered when it is added.
- A test asserting `cost-per-kg` returns `costPerKg: null` and names the missing component when any
  component read fails.

### Phase 2 — Prove isolation, settle authorization (days)

6. Run `pnpm schema:rls:prod` and `pnpm schema:isolation:prod`. Record the output and the date.
   Until this is done, treat the isolation score in §5 as provisional.
7. Resolve P1-2 either way.

**Regression tests:** if scoping is kept, a derived guard listing every route that reads a
location-scoped table and asserting it consults the allow-list. Plus an integration test with one
`user_locations` row proving a non-permitted location's rows do not appear — tamper-tested by
removing the filter.

### Phase 3 — Operational hardening, before marketing (1-2 weeks)

8. Env validation (P2-3) with a build-time failure for production-required vars.
9. Rate limiting defaults (P2-1) and `ai-validate` (P2-2).
10. Digest fan-out (P2-4): measure from `agent_runs`, then raise or split. Derive smoke targets
    from `tenants`.
11. De-duplicate `tableHasLocationColumn` (P2-5).
12. **Run the DR restore test once** (P3-1) and record the measured RTO.

**Regression tests:** a test asserting every production-required env var is declared in the schema;
a test asserting every write route resolves a rate limit; a test asserting the digest's batch size
and the orchestrator's budget are consistent with a stated tenant ceiling, so the next tenant tier
fails the test rather than the cron.

### Phase 4 — Pre-harvest, and out of audit scope

The largest *untested* risk in this product is not on the findings list, because it is an absence of
evidence rather than a defect: **the harvest chain has not executed in eight months and picking has
never executed at all.** Processing, dispatch, sales and pepper last saw real rows in February, and
three weeks of new picking code faces its first season in weeks. No amount of code reading
substitutes for running it. `docs/COMMERCIAL-LAUNCH.md` Gate 2 covers this; it should be treated as
part of production readiness, not as product work.

## Method note

Safe, existing checks that were actually run: `pnpm test` (262 files, 2,918 tests, pass, 28s),
`pnpm typecheck` (clean, re-run at the end), `pnpm lint` (1 warning, 0 errors),
`pnpm lint:dead-imports` (clean), `gh pr list` / `gh pr view`, plus read-only `git` and `grep` over
the repository and one scratch script that re-implemented a guard's scan to test its coverage
independently.

Nothing was run against production. No destructive command was issued. No secret or environment
value was read or printed — the one script that would have needed a connection string was blocked
by the permission classifier and is reported as unverified rather than worked around.

Two candidate findings were withdrawn after validation. Both are documented above rather than
deleted, because the reason each was wrong is itself a finding about how to audit this repository.
